# SelfDesk ツール実装仕様

spec-version: 1

対象: SelfDesk 向けに**個別のツールを実装する Claude**(本体の開発を担当するチャット以外すべて)。
この仕様は「何を作るか」ではなく「どこまで触ってよいか・何を残すか・どう納品するか」を決める。データ・画面・AI 連携の細部は [GOVERNANCE.md](GOVERNANCE.md) と [EXTENDING.md](EXTENDING.md) が正で、ここでは繰り返さない。
**SelfDesk の目的は「ツールがバラバラにならず、データが残り、AI から扱える」こと。** 迷ったら、この目的に近い方を選ぶ。

## 0. 役割分担

| 担当 | 持ち物 |
|---|---|
| **本体チャット**(プラットフォーム担当) | `src/types.ts` `src/store.ts` `src/core/` `src/registry.ts` `src/shell/` `src/views/` `src/theme/` `src/App.tsx` `mcp/` `scripts/` `tests/` と、全ツールの統合・検査・push |
| **ツールチャット**(あなた) | 1つのツール分の**追加ファイルだけ**(§2) |

本体の持ち物に「ちょっと手を入れれば早い」場面は必ず来る。**入れない。** §7 の依頼を書いて Kai に渡す。これが統制の要。

## 1. 着手前: 設計メモ(承認が出るまで実装しない)

1. `docs/tools/_TEMPLATE.md` を複製し、`docs/tools/<ツールID>.md` として埋める(これが後で台帳のカードになる)。
2. 次の4問([GOVERNANCE.md](GOVERNANCE.md) の §5)に答える。
   既存のどのデータで足りるか / 何を `ref` でつなぐか / 「今日」・⌘K・MCP のどこに出すか / 項目は追加のみで拡張できるか
3. 依頼が曖昧で、解釈次第で作り直しになるなら、**実装前に Kai に質問する**。推測で作り始めない。
4. 設計メモを Kai に見せ、承認を得てから実装する。

ツールID は英小文字・数字・ハイフン(2〜31 文字)。コレクションの `id`、拡張のファイル名、カードのファイル名を**すべて同じ ID にする**(検査が突き合わせる)。

## 2. 触ってよい場所

| 操作 | パス |
|---|---|
| **新規作成してよい** | `src/collections/<id>.ts` |
| | `src/extensions/<id>.tsx`(複数ファイルなら `src/extensions/<id>/` の中。ただし起動時に読まれるのは直下の `*.ts(x)` だけなので、入口を直下に置く) |
| | `docs/tools/<id>.md`(必須。設計メモ兼カード) |
| | `tests/tools/<id>.test.ts`(任意) |
| **既存ファイルへの追記だけ** | `src/collections/index.ts`(import 1行 + 配列に1項目) |
| | `docs/CHANGELOG-DATA.md`(1行追記。データ形を変えたとき) |
| | `docs/tools/README.md`(台帳に1行追記) |
| **それ以外はすべて禁止** | 特に `types.ts` `store.ts` `core/` `registry.ts` `theme/` `shell/` `views/` `App.tsx` `mcp/` `scripts/` `package.json` |

禁止の場所に変更が必要だと思ったら → §7。

## 3. データ

- 新しい種類のデータは**コレクションだけ**。`localStorage` / IndexedDB / 別ファイル / 別アプリ(単体 HTML、外部 DB、スプレッドシート)に持たない。単体 HTML 版の試作は捨てる前提でのみ可、ただし納品物には含めない。
- 項目の追加は `types.ts` を変えず、コレクションの `fields` で表す。既存の `Task` などに項目を足したくなったら §7。
- 既存の種類(タスク・予定・習慣・メモ・やりたいこと)を複製しない。`ref` で参照する。
- コレクションの `description` には「**いつ・何を記録するか**」を書く。これが AI(MCP の `collection_*`)に見える説明文になる。各 `field` の `label` / `help` も同様に、AI が読んで入力できる文にする。
- 個人情報・秘密(パスワード・トークン・口座番号)は保存しない。

## 4. 画面

- `registerView / registerWidget / registerCommand` を使い、`App` / `Shell` は触らない。
- 色・余白・角丸は `tokens.css` の変数だけ。部品は `base.css` のクラス(`.btn .field .rows .sheet` …)を使う。デザインは Quiet Pro。
  Claude の `desk-ui` スキルがある環境でも、**リポジトリ内の実装は `tokens.css` が正**(スキルは単体 HTML 用の写し)。
- 操作要素の高さ・フォーカス表示・選択状態の示し方は [HANDOFF §5](HANDOFF.md) に従う。ライト / ダーク / 幅 390px の3つで崩れないこと。
- 登録 ID は `<ツールID>.` で始める(例: `registerWidget({ id: 'books.reading', … })`)。他のツールと衝突しない。
- 認証情報(`settings.*`)に触れない。

## 5. 外部通信

拡張から `fetch` / `XMLHttpRequest` / `WebSocket` / 外部 SDK を使わない(データが同期の外に出る、秘密の置き場がない)。外部サービスが本当に必要なら、設計メモに理由を書き、§7 で本体に依頼する。

## 6. AI(MCP)

- 通常は何も書かない。コレクションを足せば `collection_*` で AI が読み書きできる。
- 専用の計算・自動処理が要るときも `mcp/src/tools.ts` は**触らない**。§7 で依頼する(現状、ツール側から MCP に専用の振る舞いを足す拡張点は無い)。
- 設計メモの「AI からの使い方」に、**AI がどんな場面でこのコレクションを読み書きすべきか**を1〜2文で書く(本体がガイド文に反映する)。

## 7. 本体への依頼(プラットフォーム変更依頼)

§2 の範囲では実現できないとき、コードを書かずに、次の形で設計メモの末尾(「本体への依頼」節)に書いて Kai に渡す。

```
- 変更してほしい場所: (例) src/types.ts の Task
- 何を: (例) Task に `energy?: 1|2|3` を追加
- なぜ: (例) 今日画面で気力に応じて並べ替えたい
- 範囲内の代替案: (例) 自前コレクションに持ち、task を ref する → 不採用の理由
```

依頼が承認・実装されるまで、そこに依存する部分は作らない(または代替案で作る)。

## 8. 完了の条件と納品形式

**リポジトリを操作できる環境**(Claude Code など)なら、`npm run check` と `npm run check:scope -- <id>` が通ること。
**操作できない環境**(チャット版)では、納品物を次の形で出す。本体チャットが取り込んで検査するので、**パスは §2 の範囲だけ**にする。

1. 先頭に `準拠: TOOL-SPEC v1`(この文書の spec-version と同じ数字)と、ツールID。
2. 変更したファイルを、**パス付きで全文**(省略・「中略」禁止)。既存ファイルへの追記は「追記する行」と「どこに」を明記。
3. 動作の確認方法(何を開いて何をすれば動くか)。確認できていない箇所は「未確認」と書く。
4. 設計メモ(`docs/tools/<id>.md`)の全文。

spec-version が古い・無い納品物は、本体側が差し戻す。

## 9. 受け入れ(本体チャット / Kai の手順)

1. `npm run check:scope -- <id>`: 触ってよい範囲を出ていないか。
2. `npm run check`: ルール検査・型・テスト。
3. 画面をライト / ダーク / 390px で確認し、MCP の `collection_list` などで AI から見えることを確認。
4. `docs/tools/README.md`(台帳)と `CHANGELOG-DATA.md` を更新し、commit。

## 10. 既知の不足(ここは待つ・依頼する)

- ツール専用の MCP ツールを足す拡張点。
- 拡張が外部 API を呼ぶ手段(秘密の保管を含む)。
- ツール間のイベント(「ツール A の完了でツール B を更新」)。今は `ref` と、AI が間に立つ運用で代替する。
